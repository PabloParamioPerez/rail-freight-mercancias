# `data/` — inputs, artefacts, and how to rebuild them

This folder holds every dataset the project reads or writes. It is organised by
**provenance and mutability**, not by topic:

| dir | meaning | mutable? |
|---|---|---|
| `raw/` | external data exactly as obtained, date-stamped | immutable |
| `external/` | third-party reference data (boundaries, numbering) | immutable |
| `interim/` | intermediate results kept for auditability | regenerated |
| `processed/` | final, reviewer-facing artefacts (CSVs, maps, DB) | regenerated |

## Reproducibility contract

Everything here is either a **pinned input** committed to git, or a **derived
artefact** that a `make` target rebuilds deterministically from those inputs.
Nothing important exists only on one machine.

```bash
make reproduce      # db → reference → lines → maps, from the committed inputs
```

Only two steps touch the network: `reference` (a one-time boundaries download,
checksum-verified) and `snapshot` (re-fetching a *new* IDEAdif photo, which you do
deliberately, not to reproduce). Everything else runs offline from the committed
`raw/ideadif_2026-07-18.gpkg`.

**Why the raw snapshot is committed** (against the usual "don't commit binaries"
rule): the IDEAdif WFS serves only a *current* snapshot, so re-fetching later does
not return byte-identical data. Archiving the exact 20 MB file is the only way to
make the whole chain reproducible. The 81 MB boundaries file is *not* committed —
it is a stable, versioned dataset, so it is fetched by URL and pinned by SHA-256
instead.

## Data dictionaries

### `lineas.csv` — one row per línea (314)
| column | meaning |
|---|---|
| `codigo_linea` | Adif catalogue code, `eje(2)+número(3)`, e.g. `01100` (the primary key) |
| `numero_rfig` | RFIG número = last 3 chars of the code (`100`); joins to Wikipedia/BOE |
| `nombre` | line name as IDEAdif ships it (station-based) |
| `wiki_linea` | endpoint name from the RFIG catalogue (blank if the número isn't listed) |
| `wiki_ancho` | track gauge: Ibérico / Estándar / Métrico / Mixto |
| `wiki_longitud` | length as the catalogue states it (cross-check vs `longitud_km`) |
| `wiki_historica` | `True` if Wikipedia greys the line as no-longer / not-yet RFIG |
| `uso_dominante` | most common `uso` across the line's tramos (blank = all unclassified) |
| `n_tramos` | number of tramos |
| `n_solo_carga` / `n_mixto` / `n_viajeros` / `n_sin_clasificar` | tramo counts by `uso` |
| `n_aptos_mercancias` | tramos usable by freight (`mercancias` + `mixto`) |
| `apto_mercancias` | `True` if any tramo is freight-usable |
| `longitud_km` | line length from the geometry (`ST_Length`, real metres) |
| `km_mercancias` | of that, how many km are freight-usable |

### `lineas_estaciones.csv` — one row per station node on a line (1 984)
| column | meaning |
|---|---|
| `codigo_linea`, `numero_rfig` | line identity (as above) |
| `orden` | position along the line (see caveat) |
| `nombre_estacion` | node name from IDEAdif, **unmodified** |
| `es_localidad` | `False` for junctions / km-points / terminals (BIF., AGUJA KM, …) |
| `municipio`, `provincia`, `ccaa` | INE municipality the point falls in, and its province / region |
| `geocode_match` | `within` (inside the polygon) or `nearest` (fell back to closest) |
| `dist_m` | metres to that municipio (0 for `within`); large only for border/port cases |
| `dep_id` | stable node id; joins to `dependencia` in the DuckDB store |

### `lineas_ciudades.csv` — one row per línea (314)
| column | meaning |
|---|---|
| `codigo_linea`, `numero_rfig`, `nombre` | line identity |
| `n_estaciones` | named nodes on the line |
| `n_municipios` | distinct municipios the line touches |
| `municipios` | those municipios, de-duplicated, in `orden`, ` > `-separated |
| `provincias` | provinces traversed, ` · `-separated |

## Two caveats a reviewer must know

1. **`orden` is geographic-approximate, not an operational stop sequence.** Nodes
   are projected onto each line's principal axis; that is exact for a corridor but
   wobbles where a line branches (e.g. línea 100's Madrid access branch). The *set*
   of municipios is reliable; the sequence is best-effort.
2. **`municipio` is where the station point physically sits** — the honest, simplified
   answer (so Pitis → Madrid). For the ~15 rows flagged `geocode_match=nearest` it is
   the nearest municipio, and two of those are correctly foreign (Valença do Minho, PT;
   Latour-de-Carol, FR). The `wiki_*` columns come from Wikipedia's transcription of
   the 2015 BOE order, a secondary source; `codigo_linea`/`numero_rfig` is the key to
   reconcile them against the primary Declaración sobre la Red when that is parsed.
